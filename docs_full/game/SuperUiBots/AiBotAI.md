# AiBotAI

**AiBotAI** is the central C++ AI controller for the SuperUiBots subsystem, acting as the in-process "body" for autonomous player characters. It bridges the gap between the VMaNGOS server engine and an external C# coordination service ("BotBrainService"), translating high-level strategic commands into low-level game actions—movement, combat, looting, and social interaction—while maintaining the bot's persistent state within the world.

Unlike standard `CreatureAI` implementations that operate purely locally, `AiBotAI` is a hybrid agent: it executes immediate reactions (combat dodges, loot rolls) locally for latency reasons, but defers long-term planning (quest routing, group composition, grind targets) to the external bridge. It manages the bot's lifecycle from database instantiation to in-world activity, ensuring the character behaves as a coherent, long-lived entity rather than a scripted stand-in.

## How the class is split

The class is distributed across six translation units, each owning a distinct slice of the bot's behavior:

*   **AiBotAI.Main**: The orchestration layer. It owns the constructor, destructor, and the primary `UpdateAI` loop that ticks every second. It handles character login, session loading, and state transitions between idle, movement, combat, and recovery. It also intercepts network packets to override default behaviors like loot rolling.
*   **AiBotAI.Bridge**: The communication seam. It manages the TCP connection to the external C# service, serializing outbound telemetry (health, position, quest log) and deserializing inbound JSON commands (move, attack, train). It contains no game logic, only transport and protocol handling.
*   **AiBotAI.Combat**: The engagement engine. It implements class-specific spell rotations, target selection, and survival mechanics (eating/drinking, mount usage). It also handles emergency scenarios like combat stalemates (getting stuck) and overpull retreats (being overwhelmed).
*   **AiBotAI.Movement**: The navigation system. It translates coordinates into safe, executable paths using the server's MMAP data. It handles path chunking for long distances, terrain correction (preventing floating), and idle wandering.
*   **AiBotAI.Grind**: The target acquisition logic. It scans the world for valid combat targets during grinding tasks, balancing efficiency (nearest target) with survival (avoiding dense packs). It supports both objective-based killing (quests) and indefinite XP grinding.
*   **AiBotAI.Loot**: The economic manager. It evaluates item quality based on class-specific weights, automates looting from corpses, and manages inventory by auto-equipping upgrades and optimizing bag space.

## How the partials collaborate

The collaboration pattern is **centralized orchestration with delegated execution**. `AiBotAI.Main` drives the cycle, but rarely acts alone:

1.  **The Tick Cycle**: `AiBotAI.Main::UpdateAI` runs every 1000ms. It first checks the bridge for new commands (`AiBotAI.Bridge::BridgeRecv`) and sends periodic state updates (`AiBotAI.Bridge::BridgeSendState`).
2.  **State-Driven Delegation**: Based on the bot's current state (dead, flying, grinding, combat), `UpdateAI` delegates to specific units:
    *   If **grinding**, it calls `AiBotAI.Grind::SelectGrindTarget` to find a mob, then `AiBotAI.Combat::AttackStart` to engage.
    *   If **moving**, it calls `AiBotAI.Movement::MoveToDestination` or `StartNextPathChunk`.
    *   If **in combat**, it calls `AiBotAI.Combat::UpdateInCombatAI` (dispatching to class-specific handlers) and checks for stalemates via `AiBotAI.Combat::HandleCombatStalemate`.
    *   If **recovering**, it calls `AiBotAI.Combat::DrinkAndEat`.
3.  **Event Feedback**: When actions occur, the executing unit notifies the bridge. For example, `AiBotAI.Loot::DoAutoLoot` sends a `LOOT` event to the C# service via `AiBotAI.Bridge::BridgeSendEvent`. Similarly, `AiBotAI.Movement::MoveToDestination` reports `MOVE_FAILED` if pathfinding breaks.
4.  **Cross-Cutting Concerns**:
    *   **Survival**: `AiBotAI.Combat::OverpullGuard` calls `AiBotAI.Grind::CountNearbyHostiles` to decide if a pull is safe.
    *   **Navigation Safety**: `AiBotAI.Movement::IsPathSafe` checks for hostile creatures along a path before committing to movement.
    *   **Gear Optimization**: `AiBotAI.Loot::ScoreItem` is called by `AiBotAI.Main::OnPacketReceived` to decide loot rolls, and by `AiBotAI.Loot::TryAutoEquip` to manage inventory.

## Data model

`AiBotAI` primarily operates on in-memory game objects (`Player`, `Unit`, `Creature`) and internal state structures. However, it interacts with the `characters` database during initialization and persistence:

*   **`characters`**: Queried by `AiBotAI.Main::OnSessionLoaded` to determine if the bot is a fresh spawn or a restart. Contains core state (level, position, money, equipment cache).
*   **`character_spell`**, **`character_skills`**, **`character_reputation`**, **`character_homebind`**, **`character_action`**: These tables are truncated for the bot's GUID during a fresh spawn to ensure a clean slate. They are not directly manipulated during runtime gameplay; changes are persisted via the standard `Player::SaveToDB` mechanism called by `AiBotAI.Main`.

No static world tables (`mangos` DB) are directly queried by `AiBotAI`; it relies on `ObjectMgr` caches for creature templates, quest data, and item prototypes.

## MCP integration

The bot bridge TCP protocol documented above (`AiBotAI.Bridge`) is also
exposed to LLM agents through MSUI's MCP server. See
[`../../admin/MCP.md`](../../admin/MCP.md) for the high-level overview.
The relevant tool class is
[`MSUI/Mcp/Tools/BotTools.cs`](../../../../MangosSuperUI/Mcp/Tools/BotTools.cs)
— 25 tools in total covering reads (`bot_list`, `bot_state`,
`bot_fleet_state`, `bot_brain_state`, `bot_brain_status`, `bot_live_state`,
`bot_fleet_report`, `bot_diag`) and commands (`bot_spawn`, `bot_move_to`,
`bot_say_text`, `bot_accept_quest`, `bot_complete_quest`,
`bot_abandon_quest`, `bot_learn_spell`, `bot_attack_target`,
`bot_interact_npc`, `bot_take_flight`, `bot_set_task_grind`,
`bot_set_task_idle`, `bot_gear_up`, `bot_toggle_brain`, `bot_form_group`,
`bot_disband_group`, `bot_auto_form_groups`, `bot_set_grouping_mode`).
All require the `bots` capability on the bearer token.
